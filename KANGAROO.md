# Kangaroo — PRD for a tile-rack discovery tool

A **kangaroo word** carries a synonym inside it. `lager` carries `ale`;
`masculine` carries `male`; `illuminated` carries `lit`. Finding them is a
letters-first activity — you stare at a word, mentally strike letters out, and
shuffle what is left until it says something.

This tool does exactly that, mechanically, with Scrabble-style tiles. **It knows
nothing.** No dictionary, no spell check, no synonym lookup, no validation, no
scoring. It is a set of game pieces and a surface to move them on. The judgement
stays entirely with the person using it.

## The one interaction, end to end

1. Type `lager`. Five square tiles — `L A G E R` — appear on a rack.
2. Press the **+** under that rack. A child rack appears below it, holding a
   duplicate of all five tiles, joined to the parent by a connector.
3. On the child rack, drag the `G` and the `R` off into the child's tray.
4. Drag the remaining three tiles into the order `A L E`.
5. The child's caption now reads **ALE**. Done — that is the discovery, recorded.

Press **+** on the parent again and you get a *sibling* to `ale`, another
five-tile rack to try a different reading on. Press **+** on the `ale` rack and
you get a *grandchild*, three tiles to whittle further. The result is a family
tree of racks: one root word, and every synonym anyone found hiding in it,
branching.

## What a rack is

A rack is a row of tile slots plus a tray. Nothing else.

- **Tiles** are square, cream, letter in the middle, small Scrabble point value
  in the corner. The value is decoration — it is a fixed letter→number table,
  never summed, never used for anything. It is there because it makes a tile
  read as a tile.
- **The rack** holds tiles left-to-right. Their order *is* the word. There is no
  separate "what does this spell" text field: the caption under the rack is
  generated by reading the tiles across, and it updates as you drag.
- **The tray** is the dimmed strip beside/below the rack holding the letters you
  have taken out. Removed letters are never destroyed — they sit in the tray,
  greyed, and drag back onto the rack at any time. Seeing the letters you spent
  is half the puzzle; a delete button that vaporises them would hide it.

**A child can only ever hold letters its parent had.** You can remove them and
return them; you cannot type a new letter into a child. That single constraint
is what makes this a kangaroo tool rather than a generic anagram scratchpad, and
it is enforced structurally — there is no UI affordance to add a foreign letter
to a non-root rack.

## The tree

| Relationship | How you get it |
|---|---|
| **Root** | Type a word into the empty state. One root per board. |
| **Child** | **+** under any rack. Duplicates that rack's *on-rack* tiles (not its tray) onto a new rack beneath it. |
| **Sibling** | **+** on the same parent a second time. |
| **Grandchild** | **+** on a child. Depth is unlimited. |

A child duplicates the parent's rack as it currently stands, at the moment you
press **+**. It is a snapshot, not a live link: rearranging the parent afterwards
does not disturb children already taken from it. This matters — otherwise every
edit upstream would scramble work downstream.

Layout is a vertical indented tree with connector rails drawn in CSS: the parent
rack, then a rail dropping to each child, children stacked in creation order.
No pan/zoom canvas, no free positioning, no SVG graph layer. Deep or wide trees
scroll. A rack can be **collapsed** to hide its subtree (the caption and a child
count stay visible) so a long session stays navigable.

## Pre-declared decisions

Taken so the MVP has no open questions blocking it. Any of these can be overridden.

| Question | Default |
|---|---|
| Dictionary / spell check / synonyms | **None, ever.** Not an MVP cut — a permanent product position. The tool is a rack, not a judge. |
| Strict kangaroo ordering | **Not enforced, not indicated.** See *The ordering question* below. |
| Adding letters to a child | **Impossible.** Root racks are the only place letters enter the tree. |
| Editing the root word | **Retype it.** Editing the root's letters after children exist would orphan them; changing the root clears the board (behind a confirm). |
| Duplicate letters | Tiles are individuals, not a set. `letter` gives three separate `T`/`E` tiles that move independently. |
| Blank tiles / wildcards | Out. |
| Case | Display is always uppercase. Input accepts anything. |
| Non-letters in the typed word | Stripped on entry. Letters `A–Z` only, so no spaces, hyphens or digits become tiles. |
| Word length | 2–15 tiles per root. Below 2 there is nothing to find; above 15 a rack stops fitting a phone. |
| Multiple trees | One root per board in the MVP. Export, then start a new one. |
| Persistence | Autosave the whole tree to `localStorage` on every change. Reload restores it. |
| Backend | None. Single page, no network requests at runtime, works with the wifi off. |

## Requirements

### Must have (this is the MVP)

- **R1 — Seed a root.** Empty state offers a text input. Submitting builds a root
  rack of uppercase letter tiles, one per letter, left to right.
- **R2 — Reorder within a rack.** Drag a tile to a new position on its own rack;
  the other tiles part to show the drop position and close up behind it.
- **R3 — Remove to tray.** Drag a tile from rack to tray. It greys and holds its
  identity.
- **R4 — Return from tray.** Drag a tray tile back to any position on the rack.
- **R5 — Spawn a child.** **+** under a rack creates a child holding a copy of
  that rack's current on-rack tiles, with an empty tray, drawn connected beneath.
- **R6 — Live caption.** Each rack shows the string its on-rack tiles spell,
  updated on every move. An empty rack shows a placeholder, not an error.
- **R7 — Delete a rack.** Removes it and its entire subtree, behind an undo (not
  a confirm dialog — undo is faster and less punishing). The root cannot be
  deleted, only cleared.
- **R8 — Undo/redo.** A stack over the whole tree, covering every mutation:
  reorder, remove, return, spawn, delete, collapse. `Ctrl/Cmd+Z` and `Shift+`
  that, plus visible buttons.
- **R9 — Touch parity.** Every drag has a tap-only equivalent (below).
- **R10 — Persistence.** Autosave to `localStorage`; restore on load; a **New
  tree** action that clears it behind a confirm.
- **R11 — Offline.** No runtime network requests of any kind. Fonts, styles and
  script are all local to the page.

### Should have

- **R12 — Export.** Copy the tree to the clipboard as an indented text outline
  (`LAGER` → `  ALE`), so a find can leave the tool and land in notes.
- **R13 — Collapse/expand** a rack's subtree, with the collapsed state persisted.
- **R14 — Sort tray** alphabetically, one button — makes a big tray scannable.
- **R15 — Shuffle rack**, one button. Randomising the tiles you are staring at is
  a genuinely useful way to break a fixation, and it is three lines of code.

### Out of scope

Dictionary, spell check, synonym lookup or any word list. Auto-solving or
suggesting. Enforcing or flagging strict kangaroo letter order. Scoring, timers,
streaks, achievements. Accounts, sync, sharing links, multiplayer. Multiple
simultaneous trees. Free-canvas layout, pan/zoom, or dragging tiles *between*
racks. Print/PDF/PNG export. Anything with a server.

## Pointer and touch

The repo's existing convention holds: pointer events, never HTML5 drag-and-drop,
which has no touch story. A press that moves under ~6px falls through to a tap,
so tap-to-select stays intact. `src/useCardDrag.ts` is the working precedent and
the drag layer should be a generalisation of it, not a second implementation.

| | Pick up | Place |
|---|---|---|
| Mouse | press and drag | release over a slot |
| Touch | press and drag | release over a slot |
| Either | **tap a tile** to select it | **tap a slot, or the tray**, to send it there |

Selection is the accessible path as well as the touch path: a selected tile can
also be moved with **←/→** (shift one position), **↓** (send to tray), **↑**
(return to the end of the rack). A tile must be reachable and operable without a
pointer at all.

## Data model

The whole application state is one serialisable tree, which is what makes undo a
stack of snapshots rather than a diff engine.

```ts
type Tile = { id: string; letter: string };   // id is stable across every move

type Rack = {
  id: string;
  tiles: Tile[];        // on the rack, left to right — the order is the word
  tray: Tile[];         // removed, still owned, still returnable
  children: Rack[];
  collapsed: boolean;
};

type Board = { root: Rack | null };
```

Invariants worth a test each:

1. A rack's `tiles ∪ tray` is exactly the multiset it was created with. Tiles are
   conserved — no move ever creates or destroys one.
2. A child's initial `tiles` equals its parent's `tiles` at spawn time, by value,
   with fresh ids.
3. Every `Tile.id` in the tree is unique, so drag targeting can never be
   ambiguous.
4. Serialise → deserialise is identity.

That is the entire domain. It is small enough that the tests are cheap and there
is no excuse for the mechanics being wrong.

## The ordering question

A flag, stated once and then deliberately not acted on.

The strict definition of a kangaroo word requires the joey's letters to appear
**in the parent's order**: `masculine` → `male` reads left to right inside it.
By that rule `lager` → `ale` is not a kangaroo word at all, because `a` follows
`l` in `lager` but precedes it in `ale` — it is an *anagram* kangaroo, a looser
and much more productive variant.

The tool takes the looser rule on purpose: free rearrangement is what makes the
tiles worth touching, and constraining drags to order-preserving moves would
turn a toy into a puzzle with a wrong answer. An **optional, purely informational
badge** on racks whose letters happen to survive in parent order would cost
little and would tell a strict-definition user which of their finds are
canonical — but it is a post-MVP item, and it stays a badge, never a restriction.

## Success criteria

The MVP is done when:

- A first-time user reproduces `lager` → `ale`, cold, in under 30 seconds,
  without instructions beyond the visible **+**.
- The same flow completes with a finger on a phone, one-handed.
- The page loads and fully works with the network disabled, and a reload restores
  the tree exactly.
- Every mutation is undoable; no action loses work permanently without an undo.
- The invariant tests above pass.

The MVP has failed if anyone using it asks "why did it say my word was wrong?" —
it must never appear to have an opinion.

## Build

Same stack as the rest of the repo: React 19 + TypeScript + Vite + Tailwind v4,
no new dependencies. It ships as its own page in the existing app, reached from
the setup screen like `RoomRunPage` is — same build, same single-file artifact
publish, no second deployment story.

Suggested slicing, each one committable and playable:

| # | Slice |
|---|---|
| 1 | `rack.ts` — the data model, mutations and invariant tests. No UI. |
| 2 | A static root rack rendered from a typed word. Tiles, values, caption. |
| 3 | Reorder + remove + return, drag and tap paths together. |
| 4 | **+**, child racks, connectors, the tree layout. |
| 5 | Delete, collapse, undo/redo. |
| 6 | `localStorage`, new-tree, text export. |
| 7 | Phone pass — rack wrapping, tap targets, one-handed reach. |

Slice 3 is the one that decides whether the tool is any good. If moving tiles
does not feel like moving tiles, nothing after it matters.
